# FRONT-002-001 — Design System

## 1. Identificação

**Issue:** FRONT-002
**Etapa:** Design System
**Tipo:** Desenvolvimento assistido por LLM

## 2. Objetivo

Implementar a primeira versão do Design System do frontend do portfólio da Erline, estabelecendo uma base visual reutilizável para as próximas etapas do projeto.

## 3. Atividades realizadas

Durante esta etapa foram desenvolvidos:

* tokens de cores;
* tokens de espaçamento;
* tokens de tipografia;
* pesos e tamanhos de fonte;
* tokens de bordas;
* tokens de sombras;
* tokens de transições;
* breakpoints;
* configuração da fonte Inter;
* componente `Button`;
* componente `Container`;
* componente `Section`;
* testes unitários dos componentes.

## 4. Decisões arquiteturais

### 4.1 Organização de componentes

Foi definida a seguinte estrutura:

```text
src/components/
├── fragments/
│   ├── Button/
│   ├── Container/
│   └── Section/
```

A pasta `fragments` representa componentes pequenos, genéricos e reutilizáveis.

Componentes específicos de uma área do portfólio deverão ser organizados posteriormente de acordo com sua responsabilidade.

### 4.2 Separação de responsabilidades

Foi estabelecida uma separação clara entre os componentes:

* `Button`: interação e apresentação de ações;
* `Container`: largura máxima e espaçamento horizontal;
* `Section`: estrutura semântica e espaçamento vertical.

Essa separação evita que um componente assuma responsabilidades que pertencem a outro.

### 4.3 CSS Modules

Foi adotado CSS Modules para isolamento dos estilos dos componentes.

Essa decisão reduz a possibilidade de conflitos entre classes e mantém os estilos associados aos respectivos componentes.

### 4.4 Design Tokens

Os valores visuais não foram distribuídos diretamente pelos componentes sempre que poderiam ser representados por tokens.

Os tokens foram centralizados em:

```text
src/styles/_variables.scss
src/styles/_typography.scss
```

Isso facilita alterações futuras na identidade visual sem necessidade de modificar individualmente diversos componentes.

## 5. Desenvolvimento assistido por LLM

O LLM foi utilizado como ferramenta de apoio durante:

* definição da estrutura inicial do Design System;
* discussão sobre organização dos componentes;
* definição de responsabilidades;
* criação inicial dos componentes;
* elaboração dos testes;
* análise de falhas nos testes;
* revisão da organização arquitetural;
* documentação técnica;
* documentação da própria utilização do LLM.

As decisões finais foram avaliadas durante a implementação e validadas por meio dos testes, lint e build do projeto.

## 6. Problemas encontrados

Durante o desenvolvimento do componente `Section`, um teste inicialmente utilizava:

```tsx
screen.getByRole("region")
```

para localizar um elemento `<section>` sem nome acessível.

O teste não encontrou o elemento dessa forma porque um `<section>` sem nome acessível não necessariamente é exposto como uma região pelo mecanismo de acessibilidade utilizado pelo Testing Library.

A estratégia de teste foi então ajustada para verificar diretamente a existência do elemento HTML `section`, mantendo `getByRole("region", { name })` quando a seção possui um nome acessível.

## 7. Validações

A etapa deve ser considerada concluída somente após a execução bem-sucedida de:

```bash
npm test
npm run lint
npm run build
```

Os testes verificam a renderização e os comportamentos relevantes dos fragmentos implementados.

## 8. Aprendizados

Esta etapa reforçou os seguintes conceitos:

* criação e utilização de Design Tokens;
* composição de componentes React;
* separação de responsabilidades;
* CSS Modules;
* acessibilidade aplicada aos testes;
* testes de componentes com React Testing Library;
* importância de validar abstrações antes de expandi-las;
* uso do LLM como ferramenta de apoio, e não como substituto da validação técnica.

## 9. Resultado

Ao final do FRONT-002, o frontend possui uma base visual inicial e componentes reutilizáveis suficientes para iniciar a construção do layout global.
