# FRONT-015 — Testes E2E

## 1. Identificação

* **Tarefa:** FRONT-015
* **Descrição:** Implementação de testes End-to-End do frontend
* **Ferramenta principal:** Playwright
* **Branch:** `feature/testes-e2e`
* **Status:** Concluído
* **Tipo:** Testes automatizados

---

## 2. Contexto

Após a implementação dos testes unitários e de integração do formulário de contato no FRONT-014, foi identificada a necessidade de validar o comportamento da aplicação através da interface.

O objetivo do FRONT-015 foi adicionar uma camada de testes E2E capaz de simular o comportamento real de um usuário utilizando o portfólio.

O primeiro fluxo escolhido foi o formulário de contato, por representar um fluxo funcional importante da aplicação.

---

## 3. Objetivos

Os objetivos definidos foram:

* adicionar Playwright ao projeto;
* configurar execução automatizada dos testes;
* separar testes E2E dos testes Vitest;
* validar o formulário de contato;
* validar cenário de sucesso;
* validar cenário de erro;
* validar campos obrigatórios;
* evitar chamadas reais ao Resend durante os testes E2E;
* preparar a estrutura para execução futura em CI/CD.

---

## 4. Decisões tomadas

### 4.1 Playwright

Foi escolhido o Playwright para os testes E2E.

A escolha foi baseada na necessidade de testar a aplicação através de um navegador real e validar os fluxos pela perspectiva do usuário.

---

### 4.2 Separação entre Vitest e Playwright

Os testes E2E foram colocados em:

```text
tests/e2e/
```

enquanto os testes Vitest permanecem em:

```text
src/
```

Essa separação evita que ferramentas diferentes tentem executar os mesmos arquivos.

---

### 4.3 API simulada

O endpoint:

```text
/api/contato
```

não é executado contra o Resend real durante os testes E2E.

O Playwright intercepta a requisição e fornece respostas simuladas.

Essa decisão evita:

* envio de e-mails reais;
* dependência de credenciais;
* dependência de serviços externos;
* testes instáveis;
* problemas de rate limit.

A integração real continua sendo validada separadamente pelo FRONT-014.

---

## 5. Implementação

Foi instalado:

```bash
npm install -D @playwright/test
```

E o navegador Chromium foi instalado com:

```bash
npx playwright install chromium
```

Foi criado:

```text
playwright.config.ts
```

E os testes foram organizados em:

```text
tests/e2e/contato.spec.ts
```

---

## 6. Cenários implementados

### Cenário 1 — Envio com sucesso

O teste preenche:

```text
Nome
E-mail
Mensagem
```

e envia o formulário.

A API simulada retorna:

```text
HTTP 200
```

O teste valida:

* requisição realizada;
* status HTTP `200`;
* mensagem de sucesso exibida na interface.

---

### Cenário 2 — Falha no envio

A API simulada retorna:

```text
HTTP 500
```

O teste valida se a aplicação apresenta:

```text
Não foi possível enviar sua mensagem. Tente novamente.
```

---

### Cenário 3 — Campos obrigatórios

O formulário é submetido sem preenchimento.

O teste valida que:

* os campos obrigatórios são respeitados;
* a requisição para a API não é realizada.

## 7. Problemas encontrados

### 7.1 Vitest executando teste E2E

Inicialmente, ao executar:

```bash
npm test
```

o Vitest tentou executar:

```text
tests/e2e/contato.spec.ts
```

Isso ocorreu porque o Vitest não estava restringido aos arquivos pertencentes à sua própria camada.

O erro apresentado foi relacionado à utilização de:

```text
test.describe()
```

pelo Playwright dentro do ambiente do Vitest.

### Solução

O `vitest.config.ts` foi ajustado para excluir:

```text
tests/e2e/**
```

Além disso, os testes de integração foram separados:

```text
src/**/*.integration.test.ts
```

Dessa forma:

```text
npm test
```

executa apenas os testes unitários e de integração simulada pertencentes ao Vitest.

Enquanto:

```text
npm run test:integration
```

executa a configuração específica de integração.

E:

```text
npm run test:e2e
```

executa exclusivamente o Playwright.

---

## 8. Problema com variáveis de ambiente

Durante a separação das suítes foi identificado que o teste de integração real precisava carregar:

```text
.env.local
```

O Vitest principal não deve carregar essas variáveis para os testes comuns.

Foi mantida uma configuração específica:

```text
vitest.integration.config.ts
```

Essa configuração utiliza:

```ts
dotenv.config({
  path: ".env.local",
});
```

A separação evita que testes comuns dependam de credenciais externas.

Nenhuma credencial foi registrada na documentação.

---

## 9. Problema com servidor Next.js

Durante os testes foi identificado conflito causado pela execução simultânea de servidores Next.js.

O diretório:

```text
.next/dev
```

pode possuir um lock enquanto uma instância de desenvolvimento já está em execução.

### Solução

O servidor passou a ser gerenciado pelo próprio Playwright através de:

```ts
webServer: {
  command: "npm run dev -- --port 3100",
  url: "http://127.0.0.1:3100",
}
```

Dessa forma, o comando:

```bash
npm run test:e2e
```

é suficiente para iniciar a aplicação e executar os testes.

---

## 10. Problema com HMR e origem de desenvolvimento

Durante a execução do Next.js foi identificada uma mensagem relacionada à origem utilizada pelo servidor de desenvolvimento.

Foi configurado:

```ts
allowedDevOrigins: ["127.0.0.1"]
```

no `next.config.ts`.

Essa configuração eliminou o aviso relacionado ao acesso do ambiente de desenvolvimento utilizado pelo Playwright.

---

## 11. Problema com `role="alert"`

Durante o teste de erro foi identificado que:

```ts
page.getByRole("alert")
```

poderia encontrar mais de um elemento na página devido a elementos internos do ambiente Next.js.

### Solução

O seletor foi restringido à seção de contato:

```ts
page.locator("#contato").getByRole("alert")
```

Essa abordagem torna o teste mais específico e reduz falsos positivos.

---

## 12. Problema com `event.currentTarget`

Durante o teste de sucesso, a API simulada retornava corretamente:

```text
HTTP 200
```

porém a mensagem:

```text
Mensagem enviada com sucesso!
```

não era encontrada pelo Playwright.

A investigação identificou que o formulário utilizava:

```ts
event.currentTarget
```

diretamente após uma operação assíncrona.

A implementação foi ajustada para preservar a referência:

```ts
const form = event.currentTarget;
```

antes do `await`.

Posteriormente o formulário passou a ser utilizado através dessa referência:

```ts
const formData = new FormData(form);
```

e:

```ts
form.reset();
```

A alteração resolveu o comportamento observado no teste E2E.

Esse problema foi importante porque o teste E2E revelou uma questão de implementação que não havia sido identificada pelas demais camadas de testes.

## 13. Aprendizados

Durante o FRONT-015 foram reforçados os seguintes conceitos:

### Testes E2E

Validam o sistema através da perspectiva do usuário.

### Mock

Permite controlar respostas externas sem depender do serviço real.

### Isolamento de testes

Cada ferramenta deve executar apenas a camada para a qual foi configurada.

### Testes determinísticos

Os testes E2E devem evitar dependências externas sempre que a integração já estiver coberta por outra camada.

### Seletores acessíveis

Foi priorizado o uso de:

```ts
getByRole()
```

e seletores semânticos sempre que possível.

### Debugging orientado pelo teste

O teste E2E ajudou a identificar um problema real relacionado ao gerenciamento do `currentTarget` durante operações assíncronas.
