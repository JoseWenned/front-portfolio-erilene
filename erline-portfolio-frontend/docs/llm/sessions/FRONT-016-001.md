# FRONT-016-001 — Implementação da Containerização com Docker

## 1. Identificação

* **Feature:** FRONT-016
* **Descrição:** Containerização do frontend
* **Branch:** `feature/docker`
* **Tecnologia:** Docker
* **Aplicação:** Next.js
* **Data:** Setembro de 2026

---

## 2. Contexto

Após a implementação dos testes E2E, a próxima etapa do frontend foi adicionar suporte à execução da aplicação através de containers Docker.

O objetivo foi permitir que o frontend pudesse ser construído e executado em um ambiente isolado e reproduzível, aproximando o projeto de uma configuração utilizada em ambientes profissionais.

A aplicação já utilizava o recurso `output: "standalone"` do Next.js, permitindo gerar uma versão otimizada da aplicação para execução em produção.

---

## 3. Objetivos

* Containerizar o frontend Next.js.
* Criar uma imagem Docker otimizada para produção.
* Separar as etapas de instalação, build e execução.
* Evitar a execução da aplicação como `root`.
* Configurar a execução através do Docker Compose.
* Manter variáveis de ambiente fora da imagem.
* Validar a execução real da aplicação dentro do container.

---

## 4. Implementação

### 4.1 Dockerfile

Foi utilizado um Dockerfile com estratégia **multi-stage build**, dividido nas seguintes etapas:

```text
base
  ↓
deps
  ↓
builder
  ↓
runner
```

### Etapa `base`

Utiliza:

```dockerfile
FROM node:22-alpine AS base
```

A imagem Alpine foi escolhida por ser uma distribuição Linux enxuta, reduzindo o tamanho da imagem final.

### Etapa `deps`

Responsável pela instalação das dependências:

```dockerfile
COPY package.json package-lock.json ./
RUN npm ci
```

O uso de `npm ci` garante uma instalação baseada no `package-lock.json`, proporcionando maior previsibilidade no ambiente de build.

### Etapa `builder`

Responsável pela compilação da aplicação:

```dockerfile
COPY --from=deps /app/node_modules ./node_modules
COPY . .

RUN npm run build
```

O build gera os artefatos necessários para execução do Next.js em modo standalone.

### Etapa `runner`

É utilizada como imagem final de produção.

Foram copiados apenas os artefatos necessários:

```dockerfile
.next/standalone
.next/static
public
```

Também foi criado um usuário específico para executar a aplicação:

```dockerfile
RUN addgroup --system --gid 1001 nodejs \
    && adduser --system --uid 1001 nextjs

USER nextjs
```

Dessa forma, a aplicação não é executada como `root`.

## 5. Docker Compose

Foi criado um `docker-compose.yml` para facilitar a execução do frontend:

```yaml
services:
  frontend:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: erline-portfolio-frontend
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: production
      NEXT_PUBLIC_API_URL: http://localhost:8080
      HOSTNAME: 0.0.0.0
    restart: unless-stopped
```

O Compose permite centralizar a configuração necessária para executar o container e facilita a reprodução do ambiente.

## 7. Decisões técnicas

### Multi-stage build

A estratégia multi-stage foi escolhida para separar o ambiente de construção da imagem final.

Isso permite que dependências e arquivos utilizados apenas durante o build não sejam incluídos desnecessariamente na imagem de produção.

### Next.js Standalone

O projeto já estava configurado com:

```typescript
output: "standalone"
```

Esse recurso permite gerar uma estrutura contendo apenas os arquivos necessários para executar a aplicação.

### Usuário não-root

O container executa a aplicação com o usuário `nextjs`, reduzindo privilégios dentro do container.

### Variáveis de ambiente

As variáveis de ambiente não são incorporadas ao código-fonte ou à imagem Docker.

A configuração é fornecida durante a execução do container.
