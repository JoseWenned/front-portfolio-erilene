# FRONT-017-001 — Configuração de CD e Deploy na Vercel

## 1. Identificação

**Feature:** FRONT-017 — CD: Deploy do frontend na Vercel
**Sessão:** FRONT-017-001
**Projeto:** Erline Portfolio Frontend
**Branch:** `feature/cd-vercel`
**Status:** Em desenvolvimento

---

## 2. Contexto

O frontend do portfólio da Erline possui uma pipeline de Integração Contínua (CI) configurada com GitHub Actions, responsável por validar alterações antes que sejam integradas à branch `main`.

Com a implementação da containerização no FRONT-016, o projeto também passou a possuir uma estratégia de execução em ambiente Docker.

Nesta etapa, o objetivo é implementar o processo de **Continuous Deployment (CD)** utilizando a Vercel como plataforma de hospedagem e deploy da aplicação Next.js.

A escolha da Vercel está alinhada à tecnologia utilizada no projeto, permitindo integração direta com o GitHub e automatização do processo de build e publicação da aplicação.

---

## 3. Objetivos

Esta sessão tem como objetivos:

* configurar a aplicação frontend na Vercel;
* integrar o repositório GitHub à Vercel;
* definir a branch `main` como branch de produção;
* configurar as variáveis de ambiente necessárias;
* estabelecer o deploy automático após alterações na `main`;
* validar o processo de build e publicação;
* documentar a estratégia de Continuous Deployment;
* manter o CI existente separado da responsabilidade de CD.

---

## 4. Estratégia de CI/CD

A arquitetura de entrega do frontend será dividida entre GitHub Actions e Vercel.

```text
Desenvolvimento
      │
      ▼
Feature Branch
      │
      ▼
Pull Request
      │
      ▼
GitHub Actions
      │
      ├── Lint
      ├── Testes
      ├── Testes E2E
      └── Build
      │
      ▼
Merge na main
      │
      ▼
Vercel
      │
      ├── Build
      └── Deploy
      │
      ▼
Produção
```

### Responsabilidades

**GitHub Actions**

Responsável por validar a qualidade do código antes da integração com a branch `main`.

**Vercel**

Responsável pelo processo de Continuous Deployment após a integração da alteração na branch de produção.

Essa separação evita que o workflow de CI precise assumir responsabilidades de infraestrutura e publicação.

---

## 5. Escolha da Vercel

A Vercel foi escolhida como plataforma de hospedagem devido à integração nativa com aplicações Next.js e à possibilidade de conectar diretamente um repositório GitHub.

A plataforma permite que o processo de deploy seja acionado automaticamente a partir de alterações no repositório.

Para este projeto, a estratégia adotada será:

```text
main
 │
 └── Deploy automático
          │
          ▼
       Vercel
          │
          ▼
     Produção
```

O processo de deploy não será executado manualmente a cada alteração.

---

## 6. Integração com o GitHub

O projeto será conectado à Vercel por meio do repositório GitHub.

A branch `main` será utilizada como referência para o ambiente de produção.

Branches de feature continuarão sendo utilizadas durante o desenvolvimento:

```text
feature/*
    │
    ▼
Pull Request
    │
    ▼
main
    │
    ▼
Vercel Production
```

Dessa forma, alterações ainda em desenvolvimento não serão publicadas diretamente no ambiente de produção.

---

## 7. Configuração do projeto

A aplicação utiliza Next.js e possui o processo padrão de build definido no `package.json`.

O build de produção será executado pela própria Vercel.

A configuração deverá utilizar:

```text
Framework: Next.js
Build Command: npm run build
Install Command: npm ci
Output: Next.js
```

O deploy não dependerá do Dockerfile criado no FRONT-016.

O Docker continuará disponível para execução local e validação de uma imagem de produção, enquanto a Vercel utilizará seu próprio ambiente de build e execução para o deploy.

---

## 8. Variáveis de ambiente

A aplicação possui variáveis de ambiente utilizadas pela integração de contato.

As seguintes variáveis deverão ser configuradas na Vercel:

```text
RESEND_API_KEY
CONTACT_EMAIL_TO
```

Esses valores não devem ser versionados no Git.

O arquivo `.env.local` permanece apenas no ambiente de desenvolvimento local.

A chave da API do Resend deverá ser armazenada como segredo na configuração da Vercel.

### Regra de segurança

Nenhuma credencial ou segredo deverá ser inserido diretamente no código-fonte.

A configuração deverá seguir:

```text
Desenvolvimento
    │
    └── .env.local
           │
           └── não versionado

Produção
    │
    └── Vercel Environment Variables
```

---

## 9. Ambiente de produção

A branch `main` será associada ao ambiente de produção.

Sempre que uma alteração for integrada:

```text
Pull Request
     │
     ▼
CI aprovado
     │
     ▼
Merge na main
     │
     ▼
Vercel detecta alteração
     │
     ▼
Build
     │
     ▼
Deploy
```

O objetivo é que a versão disponível em produção represente o estado validado da branch `main`.

---

## 10. Processo de Deploy

O processo esperado é:

### 1. Desenvolvimento

A implementação ocorre em uma branch específica da feature.

### 2. Pull Request

A feature é enviada para revisão através de Pull Request.

### 3. CI

O GitHub Actions executa as validações configuradas.

### 4. Merge

Após a aprovação, a alteração é integrada à `main`.

### 5. Build na Vercel

A Vercel identifica a alteração e inicia o processo de build.

### 6. Deploy

Após o build ser concluído com sucesso, a aplicação é disponibilizada no ambiente de produção.

---

## 11. Relação com Docker

A utilização da Vercel não elimina a implementação realizada no FRONT-016.

O Docker possui uma finalidade diferente dentro do projeto.

### Docker

Utilizado para:

* padronizar o ambiente de execução;
* validar a aplicação em um container;
* reproduzir um ambiente de produção localmente;
* estudar e aplicar conceitos de containerização.

### Vercel

Utilizada para:

* hospedagem da aplicação;
* build de produção;
* deploy automático;
* integração com GitHub;
* disponibilização pública do frontend.

Portanto, as duas estratégias são complementares.

```text
Docker
 └── Execução e validação local

Vercel
 └── Hospedagem e Continuous Deployment
```

## 13. Decisões técnicas

### 13.1 Vercel como plataforma de deploy

A Vercel foi escolhida por possuir integração direta com Next.js e GitHub, reduzindo a complexidade necessária para disponibilizar o frontend em produção.

### 13.2 Deploy automático pela `main`

A branch `main` representa o estado de produção do projeto.

O deploy automático reduz a necessidade de execução manual e estabelece um fluxo contínuo entre código validado e aplicação publicada.

### 13.3 CI e CD separados

O GitHub Actions continuará responsável pelo CI.

A Vercel será responsável pelo CD.

Essa separação mantém cada ferramenta focada em uma responsabilidade específica.

### 13.4 Docker mantido no projeto

A containerização implementada anteriormente continuará fazendo parte do projeto mesmo com o uso da Vercel.

Ela representa uma estratégia independente de execução e contribui para a portabilidade da aplicação.

---

## 14. Segurança

As credenciais utilizadas pela aplicação não deverão ser armazenadas no repositório.

Particularmente:

```text
RESEND_API_KEY
```

deve permanecer exclusivamente no ambiente de execução.

O `.env.local` permanece no `.gitignore` e não deve ser enviado para o GitHub.

Também não devem ser utilizadas variáveis `NEXT_PUBLIC_*` para informações secretas.
