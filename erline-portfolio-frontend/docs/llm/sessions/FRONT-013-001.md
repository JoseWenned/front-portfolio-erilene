# FRONT-013-001 — Integração com Resend

## Identificação

* **Feature:** FRONT-013 — Integração com Resend
* **Sessão:** FRONT-013-001
* **Objetivo:** Implementar e validar o envio do formulário de contato através do Resend.
* **Branch:** `feature/integracao-resend`

---

## 1. Contexto

A seção de contato do portfólio já possuía o formulário visual e passou a ter comportamento interativo.

O objetivo desta etapa foi permitir que os dados enviados pelo visitante fossem processados por uma API Route do Next.js e encaminhados para um endereço de e-mail através do Resend.

O backend Spring Boot não foi utilizado nessa funcionalidade, pois o envio de e-mail não exige processamento de domínio ou persistência no backend.

---

## 2. Decisão de arquitetura

Foi adotado o seguinte fluxo:

```text
Visitante
    ↓
Formulário de contato
    ↓
POST /api/contato
    ↓
Next.js Route Handler
    ↓
Resend API
    ↓
E-mail da cliente
```

A API Route foi definida como fronteira de integração entre a aplicação e o serviço externo.

A chave da API do Resend permanece exclusivamente no ambiente do servidor.

---

## 3. Implementação

Foi criada a rota:

```text
src/app/api/contato/route.ts
```

A rota é responsável por:

* ler as variáveis de ambiente;
* validar a existência das configurações necessárias;
* receber os dados enviados pelo formulário;
* validar os campos obrigatórios;
* instanciar o cliente Resend;
* enviar o e-mail;
* tratar erros;
* retornar respostas HTTP apropriadas.

As configurações utilizadas são:

```env
RESEND_API_KEY=re_...
CONTACT_EMAIL_TO=email-da-cliente
```

A variável `RESEND_API_KEY` não deve ser exposta ao cliente.

---

## 4. Remetente, destinatário e resposta

Durante o ambiente de testes foi utilizado o remetente disponibilizado pelo Resend:

```text
Erline <onboarding@resend.dev>
```

O endereço configurado em `CONTACT_EMAIL_TO` representa o destinatário das mensagens.

O e-mail informado pelo visitante é utilizado através de `replyTo`.

Dessa forma:

```text
FROM
Remetente configurado no Resend

TO
E-mail configurado em CONTACT_EMAIL_TO

REPLY-TO
E-mail informado pelo visitante
```

Em produção, após a aquisição e verificação de um domínio próprio da cliente, o remetente poderá utilizar um endereço profissional baseado nesse domínio.

---

## 5. Problemas encontrados durante a implementação

### 5.1. Porta incorreta

Inicialmente foi realizada uma requisição para uma aplicação diferente que estava executando na porta `3000`.

Isso resultou em uma resposta `404`.

Foi identificado que o projeto atual estava executando na porta `3001`.

A requisição foi então direcionada para:

```text
http://localhost:3001/api/contato
```

---

### 5.2. API Key inválida

Durante o primeiro teste com o Resend foi utilizada uma chave inválida.

A API retornou:

```text
401 Unauthorized
```

Foi corrigida a configuração da variável:

```env
RESEND_API_KEY
```

Após a correção, a autenticação passou a funcionar.

---

### 5.3. Destinatário inválido

Em um teste inicial, a implementação utilizava um valor de placeholder:

```text
SEU_EMAIL_DE_TESTE
```

O Resend retornou:

```text
422
Invalid `to` field.
```

O problema foi corrigido substituindo o placeholder por uma variável de ambiente:

```env
CONTACT_EMAIL_TO
```

---

### 5.4. Restrição do ambiente de testes

Após a autenticação e o destinatário correto, o Resend retornou:

```text
403
```

informando que a conta de teste somente permite o envio para o próprio endereço autorizado até que um domínio seja verificado.

Esse comportamento confirmou que:

* a API Key estava válida;
* a comunicação com o Resend estava funcionando;
* a limitação estava relacionada às regras do ambiente de testes.

A configuração de domínio próprio ficou definida como etapa futura.

---

## 6. Testes automatizados

Foram implementados testes unitários para o Route Handler.

O cliente Resend é mockado através do Vitest.

A estrutura testada é:

```text
POST /api/contato
       ↓
Route Handler
       ↓
Resend mockado
```

Foram contemplados os seguintes cenários:

### Sucesso

Verifica:

* status `200`;
* chamada ao Resend;
* utilização do `replyTo`;
* construção do assunto.

### Campos obrigatórios ausentes

Verifica:

* status `400`;
* ausência de chamada ao Resend.

### Erro retornado pelo Resend

Verifica:

* status `500`.

O objetivo dos testes unitários é validar o comportamento da aplicação sem depender da disponibilidade do serviço externo.

---

## 7. Validação real

Além dos testes unitários, foi realizada uma validação manual utilizando a API real do Resend.

A validação permitiu verificar a comunicação entre:

```text
Cliente HTTP
    ↓
Next.js
    ↓
Route Handler
    ↓
Resend real
```

A integração real foi considerada validada dentro das limitações impostas pela conta de testes.

---

## 8. Decisão sobre teste automatizado contra o Resend

Não será criado neste momento um teste automatizado executando contra a API real do Resend.

A integração externa já foi validada manualmente.

A automação desse cenário ficará condicionada à configuração de um domínio próprio da cliente.

Motivos:

* dependência de serviço externo;
* necessidade de credenciais reais;
* dependência de internet;
* possibilidade de instabilidade externa;
* restrições do ambiente de testes;
* possibilidade de envio real de e-mails;
* necessidade de configuração adequada do domínio.

Os testes unitários permanecem como parte da suíte executada normalmente pelo CI.

---
